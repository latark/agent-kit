# agent-kit

Маркетплейс плагинов Claude Code для системы агентов «Пантеон». Общие части собираются здесь сразу,
поэтому на другой установке работает то же, что у владельца; роли армии, хранилище знаний и ключи у каждого свои.
Приватный репозиторий `latark/agent-kit`; ведёт его metis-pantheon (изменения — после «да» владельца).

| Плагин | Что делает | Состояние |
| --- | --- | --- |
| `guard` | Правила, которые Claude Code проверяет сам: dev-server, attribution, cdp, tg-secret, nextjs, domain, pantheon-acl, protect-config, private, cdp-role, push, terminal; модель угроз и режимы — `plugins/guard/README.md` | работает с 14.10 (шаг 0.4); управляемые настройки — шаг 0.6, ставятся через `sudo` |
| `pantheon` | Планировщик `pantheon-tick` (launchd, раз в 60 с), команда `pantheon`, копия `~/ai/pantheon-view` для Obsidian, задачи и доска владельца, коммит `~/ai/pantheon`, настройки окон ролей с песочницей и строгим guard, сверка карты решений; хуки контекста (подсказка «пора очистить», продолжение после `/clear`, файл состояния после сжатия) и журнал ваших слов owner-log; запуск сессий (`pantheon start`, `wake`; откуда запуск, берётся из `--from`, а без него из окна: `PANTHEON_ROLE=hq` — zeus, другая роль — tick, без роли — вы, и в окне роли явный `--from` должен совпадать с origin окна (hq — zeus, другая роль — tick), иное, в том числе `--from owner`, — отказ, код 2; zeus без вашего слова в окне Зевса — отказ, код 2, и у `--at` при постановке; `start` пишет замер загрузки Mac в `capacity.jsonl`, красный замер или «нет сигнала» (своп и давление не прочитаны) без вашего слова — код 5 «отложено», не сбой: самозапуск и разовый запуск повторяются; `start --from tick`, проигравший гонку за имя (блокировка имени занята другим процессом или под блокировкой уже стоит живая копия с id) — код 4 «пропуск», не сбой, строки `start-busy` / `start-skip` в `start.log` (у `--from owner`, вкладки без id и подложенной записи блокировки — код 1, metis-0717); `wake` пишет строку замера и красной зоной не откладывает, кроме `wake hestia` из окна роли (не hq): со словом в красной зоне — код 5, без слова — код 2; `wake <имя> "задание"` из окна роли (задан `PANTHEON_ROLE`) без вашего слова в окне Зевса за 15 мин — отказ, код 2, сессия не поднимается (строка замера «refused»), без задания `wake <имя>` будит с «продолжай» и слова не требует; дежурный зовёт дочерний `pantheon start` без роли окна, поэтому `pantheon watch`, запущенный из окна Зевса, самозапуск не ломает; разовый запуск `start --at` исполняется по правилам планового прохода: в красной зоне ждёт, слово при постановке не переносится), сборка ролей (`pantheon roles build`), заранее разрешённое (`pantheon approve`), обёртка `heavy`, Stop-хук разработчика; дежурный без модели (`pantheon watch`: сессии, swap, worktree, версия Claude Code, паузы, самозапуск по вашим решениям, журналы ваших слов), пересмотры, остановка и пауза, технический перезапуск, продолжение сессий `claude respawn` с текстом через хук | работает с 14.10 (шаг 0.4); хуки — с шага 1.1; роли и запуск — с шага 1.2; дежурный и перезапуск — с 0.10.0 (шаг 1.4) |
| `project-tools` | Инструменты проекта по карте стеков `stacks.json`: MCP-серверы (next-devtools, chrome-devtools, shadcn) — в `.mcp.json` проекта с одобрением, плагины (Supabase) — в настройки проекта, блок для Codex; команда `project-tools` (check, apply, skip, outdated), навык, подсказка при старте сессии; отпечатки одобренных записей — предупреждение о подмене после `git pull` | с 14.10 (шаг 0.7) |

## Где что лежит

- `plugins/guard/hooks/guard_rules.py` — все правила guard; шапка файла перечисляет их и выключатель `GUARD_OFF`.
  Хуки зовут короткий вход `plugins/guard/hooks/guard.py`: он грузит правила из кэша .pyc (metis-0148).
  Данные: `~/.local/state/pantheon/domains.json` (собирает `pantheon domains build` из
  `~/ai/pantheon/directions.toml`) и `~/.claude/pantheon/policy.toml` — привилегии (образец —
  `plugins/guard/policy.example.toml`), правит только metis-pantheon.
- `plugins/pantheon/lib/pantheon.py` — планировщик и команда; `pantheon help` — список команд.
  Группы команд вынесены в модули `lib/` (metis-0586): `review`, `plugins`, `taskcli`, `consent`, `jobs`, `archive`,
  `quarantine`, `instructions`, `rolecmd`, `sessions`. `pantheon.py` подключает их через `_attach`: их имена остаются
  именами `pantheon`, а сами модули зовут pantheon через `P`. Сборка окон (`sandbox_build` и всё, на что она ссылается)
  остаётся в `pantheon.py`: признак ядра в шлюзе guard (metis-0404) смотрит только этот файл.
  Задачи — `~/ai/pantheon/schedule.toml`, метки и журналы запусков — `~/.local/state/pantheon/` (свои у каждого Mac).
- Требуется Python 3.11+ (`tomllib`). Системный `/usr/bin/python3` на macOS — 3.9, он не подходит; `bin/pantheon` и
  `bin/pantheon-tick` сами ищут 3.11+ (`lib/find-python.sh`): `PANTHEON_PYTHON`, затем `python = "…"` из
  `STATE/config.toml` (его пишет `pantheon-setup`), затем `python3` из PATH, `python3.14`…`3.11`, Homebrew, python.org.
  Не нашли — строка «нужен Python 3.11+» и код 1, у планового прохода ещё строка в `alerts.md` не чаще раза в сутки. Новой установке
  Python ставит `pantheon-setup` (uv, Python 3.14); вручную — `brew install python@3.14`. Хуки guard и pantheon тоже
  идут на 3.11+ (metis-0571): их запускает `hooks/python.sh` — ищет `python3.14`…`python3.11` в `/opt/homebrew/bin`,
  `/usr/local/bin`, python.org и PATH, затем `python3` из PATH с проверкой версии. Не нашёл — PreToolUse
  останавливает действие с кодом 2 и строкой «нужен Python 3.11+», остальные хуки молчат (код 0). Так же — пропавший
  файл скрипта хука (metis-0330): Python сам вышел бы с кодом 2, и Stop с UserPromptSubmit вставали бы во всех окнах.
  Каждый такой отказ — строка `launcher` в `~/.local/state/pantheon/logs/guard-failures.log`. Хук отключают правкой
  записи в hooks.json, а не переименованием файла. guard.py, запущенный
  старым `python3 guard.py` (managed settings до переустановки, старые настройки окон), на 3.9 сам перезапускается
  через `hooks/python.sh`. `pantheon infra-check` показывает строки «Python установки» и «запускатель хуков».
- Установка для нового человека (macOS): `plugins/pantheon/bin/pantheon-setup` из клона agent-kit, одной командой.
  Загрузчик на bash до всего проверяет, что это macOS, что `~/ai/pantheon` (`PANTHEON_HOME`) нет или он пуст, что `claude`
  на PATH и клон — репозиторий; при отказе ничего не ставит. Дальше ставит uv (`UV_NO_MODIFY_PATH=1`, профили
  оболочки не правит) и Python 3.14, уже стоящие Python не трогает, и передаёт дело `lib/setup.py`. Он идёт по шагам,
  у каждого итог «ок / пропуск / не вышло»: путь Python в `config.toml`; маркетплейс и плагины guard, pantheon,
  project-tools; пустой `~/ai/pantheon` из `plugins/pantheon/template/pantheon/` с `git init`; `pantheon install`;
  `pantheon roles build`; вход git в GitHub через gh (`gh auth setup-git` — только после явного «да»);
  резервная копия (ниже); terminal-notifier; проверка личных следов (`scripts/check-traces.py` по файлам установщика и собранным ролям, маркеры —
  `--markers ФАЙЛ` или `PANTHEON_TRACE_MARKERS`, нет файла — пропуск); Codex (`--codex`, `--no-codex`, без флагов —
  вопрос, по умолчанию нет). До push — `pantheon traces` (та же проверка, что CI check-traces, по файлам репозитория; маркеры —
  `--markers ФАЙЛ`, `PANTHEON_TRACE_MARKERS` или `~/.config/pantheon/trace-markers.txt`; нет файла — отказ, код 2) и
  `pantheon traces install-hook` (pre-push в репозитории, без молчаливой замены чужого хука). `pantheon-setup --add codex` — только шаг Codex на готовой установке. К системе
  `setup.py` ходит через `lib/platform_macos.py` (Homebrew, launchd, sandbox-exec, Связка ключей, текст про
  уведомления). Тест — `plugins/pantheon/tests/test_setup.py`, все внешние программы в нём — заглушки.
- Резервная копия (metis-0476): шаг установщика после входа в GitHub и `pantheon-setup --add backup` на готовой
  установке. Идёт, только если gh вошёл и стоит git-crypt (`brew install git-crypt`), и только после «да» на вопрос;
  иначе строка «копии нет: при потере Mac данные пропадут». Уже задан `origin` — пропуск, второй репозиторий не
  заводится. Порядок: `git-crypt init` → ключ (`git-crypt export-key` во временный файл в `$TMPDIR`, сразу удаляется)
  base64 в Связку ключей через stdin (`security -i`, ключа нет в аргументах процесса; запись после добавления проверяется), служба `pantheon-git-crypt` (запись уже есть — отказ, старый ключ не перезаписывается) →
  `.gitattributes` (`* filter=git-crypt diff=git-crypt`, `.gitattributes` и `.gitignore` открыты) → снимок: коммит
  без родителей, ветка переставляется на него, прежняя история остаётся локально в `refs/pantheon/pre-backup`, при повторе после сбоя — `pre-backup-2` и т. д., коммиты между попытками не теряются (иначе
  старые коммиты ушли бы в GitHub открытыми; об этом прямо говорит вопрос до «да») → проверка, что каждый файл снимка начинается с заголовка git-crypt →
  только потом `gh repo create <имя> --private` (`--backup-name ИМЯ`, по умолчанию `pantheon-hq`), `origin` и
  `git push -u`. Сбой до GitHub ничего снаружи не создаёт. Связка ключей не уходит в iCloud, поэтому установщик
  просит сохранить ключ ещё и вне Mac (менеджер паролей; показать — `security find-generic-password -s
  pantheon-git-crypt -w`). Вернуть на другом Mac, положив ключ в его Связку под той же службой: `git clone <адрес> ~/ai/pantheon`, затем в этой папке
  `security find-generic-password -s pantheon-git-crypt -w | base64 -d > "$TMPDIR/k" && git-crypt unlock "$TMPDIR/k"`
  и `rm "$TMPDIR/k"`.
- Настройки человека — `STATE/config.toml` (`~/.local/state/pantheon/`, свои у каждого Mac): `python`, таблица
  `[executors] set` (Claude всегда, Codex — дополнение) и `[codex]` (состояние проверки). Читает и пишет только
  `lib/pconfig.py` (`load`, `update`).
- Исполнители (`lib/executors.py`): `pantheon executors` — набор и состояние, `check` — проверка Codex (на PATH, вход,
  hello-проба), `--add codex`, `--remove codex`, `pick <id задачи>` — кто пишет задачу. `pantheon exec codex <папка
  worktree> <файл поручения>` — запуск Codex в worktree; коды выхода: 0 — коммит есть, 1 — отказ (ошибка хода,
  защищённые пути, нет изменений), 2 — неверный вызов или worktree не чистый (игнорируемое не в счёт), 3 — Codex
  недоступен (задачу на dev-*), 4 — занят.
- Лёгкий плановый проход: `pantheon` идёт модулем через `lib/run.py` (байт-код в `lib/__pycache__`, при read-only папке молча
  без кэша), `--help` ~34 мс вместо ~62. Задачи `view --quiet`, `board`, `sync-answers`, `agents` плановый проход пропускает, если
  их входы (отпечаток stat, таблица входов — `TICK_SKIP` в `lib/pantheon.py`) не менялись с прошлого удачного прогона;
  не реже раза в 15 минут они идут в любом случае, ручной вызов и `run-job` — всегда. Пропуски — `tick-skipped.json`.
- Проход доски (metis-0709): журнал задания `board` печатает строку «доска-время: реестр · статусы · блокировка-notify · карточки · очистка · сводка — с каждой частью, прерванная часть и итог». Бюджет прохода — `PANTHEON_BOARD_BUDGET`, по умолчанию 45 с при пределе задания 60 с. Ожидание блокировки notify — не дольше 20 с и не дольше остатка бюджета; занят дольше — проход идёт без уведомлений. Сводка `board-auto` пропускается, если до бюджета осталось меньше 8 с. Пропуски названы в строке «пропущено». Зависший `terminal-notifier` (предел 15 с) или `osascript` (10 с) не обрывает проход.
- Недельный потолок владельца (с 0.11.100, metis-0403; формат — шапка `lib/night.py`): `[limits.owner_cap]` в
  `schedule.toml` (`pct`, `decision`, срок `until`/`since`, старый дневной `date`). Неделя ≥ `pct` — отказ самозапуску,
  `wake` и `respawn` дежурного днём и ночью и новым субагентам из окон координаторов, мастерской и Пританея (хук PreToolUse
  `Agent|Task` → `pantheon night agent-gate`); зоны и ночь потолок не снимает. С metis-0444 он же держит ручные
  `pantheon start` и `wake` (все виды, кроме `start zeus` и Гестии — `wake hestia`, решение владельца 29.10), запуск по вашему ответу в окне вопросов (отказ, код 2) и
  задачи `claude -p` планового прохода (ждут, срок не сдвигается). Сверх потолка — только из вашего терминала флагом `--over-cap`.
  Одна тревога и одна карточка Зевсу на неделю и `pct`; `pantheon night status` показывает потолок и запас.
- Запуск без СБ ([sb-simplify] п. 5 и 10, metis-0523, metis-0564). Окна по ответу владельца: вопрос Зевса в окне
  вопросов строго по шаблону `pantheon launch-question <id> запустить|перезапустить|вернуть <направление>` и выбор
  «Да — <глагол> <имя>» плановый проход исполняет сам (`word_launch` в `lib/watch.py`); любое отличие, заметка или свой
  текст — отказ. «Остановлено вами» снимает только «Да — вернуть <имя>» (затем окно поднимается) или `pantheon resume`;
  запустить и перезапустить остановленное не трогают. Каждое поручение — строка
  `word-launch` в `logs/start.log` и строка в `alerts.md`; запись исполняется один раз, не старше 12 ч. Своп и давление
  памяти запуск не откладывают: только предупреждение в stderr и тревога раз в день. Окно Зевса пишет только в
  `STATE/hq-rw/locks` (замки имён сессий `start-*`, `wake`) и `STATE/hq-rw/autostart-reset`; замки прохода — в
  `STATE/locks`, куда окно не пишет. Файл в `hq-rw` открывается с `O_NOFOLLOW|O_NONBLOCK` и проверкой `fstat`
  (обычный файл, одна ссылка, свой владелец); ссылка, FIFO или папка на месте записи — отказ блокировки с предупреждением,
  а не падение start и прохода. Ждущая блокировка там ждёт не больше 60 с; `pantheon stop` без блокировки вслепую не
  останавливает: ставит метку «остановлено вами» и выходит с кодом 1 — повторить. Ночь (вариант Б, 28.10): фиксированного вопроса в 22:00 нет, ночь открывается только ответом «Да — ночь
  <дата>» на вопрос `pantheon night ask <id> <направление>` о ночной пачке; в вопросе — путь и sha256 пачки, проход
  сверяет ответ дословно и sha256 файла, изменённая пачка не идёт. Без такого ответа ночью новое не запускается.
  Самозапуск не отдаёт координатору задачу, которую ведёт другая сессия (`owner` вне направления и его команды).
  Задачу из цели окна (`/goal` самозапуска) передали другой сессии, перенесли, вернули во входящие или отменили —
  плановый проход в тот же проход перезапускает окно свежей сессией с новой целью по оставшимся и следующим задачам
  очереди. Очереди нет или подъём закрыт, а своих задач у сессии не осталось — останавливает (claude stop + rm); свои
  ещё в работе — оставляет до открытия подъёма, тревога. Ждущую вас сессию не трогает. Имя держит ещё одна сессия
  (владелец поднял окно вручную) — смена откладывается, никого не гасит (metis-0631).
  Повторная проверка под блокировкой имени перед подъёмом или передачей задания сказала «не надо» (окно уже работает,
  его остановили, поднимает другой процесс) — это пропуск, а не сбой: без тревоги «код 4» и без счётчика сбоев, строка
  `resume-skip` в `start.log` (metis-0708). То же у продолжения после паузы и запуска по ответу владельца (в тревоге
  «пропуск — причина»), а разовый запуск после пропуска не гасится и без уведомления «не вышел» ждёт до срока.
  Новое поручение посреди сессии входит в её цель (metis-0276): условие `/goal` координатора (`TASK_GOAL`,
  `COORDINATOR_GOAL` в `lib/sessions.py`) говорит, что поручение Зевса или владельца, пришедшее позже, — часть цели, а
  «готово» с «перехожу к …» её не закрывает. Задача поручения уходит из цели, только когда ждёт ответа владельца на
  вопрос (`waiting_on=human` и `question`) или другую задачу (`waiting_on=<id>`), которая её правда держит: блокер
  есть, не done и не dropped, а если сам ждёт — тоже снят с цели. Тогда `pantheon task set` печатает «<id>: снята с
  цели окна», и Stop-хук цели её больше не требует; верит он последней такой строке по задаче. Другой блокер,
  несуществующий id, цикл ожиданий — «остаётся в цели окна», как задача в работе; задачи в работе и в очереди — в
  цели (metis-0714). Блокер потом закрыли (done, dropped) или он сам стал ждать без основания — `task set` по блокеру
  печатает «<id>: остаётся в цели окна — блокер <B> <статус>» про каждую ждущую его задачу, и по цепочке тоже.
  «Снята» верна на момент записи: плановый проход сам возвращает задачу в doing и в транскрипт не пишет, поэтому
  задача, чей статус вернулся в doing или todo, — снова в цели.
  Сменить цель живой фоновой сессии извне нечем, поэтому так. Координатор
  закончил ход или его сессии нет, а в `inbox/` — поручение Зевса, написанное после конца хода и по вашему слову ему
  (запись в `owner-log/zeus.md` за 15 мин до файла и ещё 10 мин на проход): плановый проход поднимает новую сессию с
  целью по нему (`pantheon start --from tick`, проверка «поручения во входящих», `inbox_wake` в `lib/awake.py`). Время

  pytest; `--sha <head>` — на этом коммите в своей копии прохода `work/test-<ID>`, когда ветку PR не переключить в
  worktree окна из-за `.claude/` проекта, metis-0779) или `pantheon outside serve` (metis-0614: своя копия на коммите — `--sha` или HEAD папки — в
  `~/Library/Caches/pantheon-outside/work/<ID>`, в монорепо PORT одному приложению — `--app`; скрипт dev → адрес
  `http://127.0.0.1:<4300–4399>` мимо портов владельца 3000 и 3100–3299; не больше двух серверов, при давлении памяти —
  отказ с причиной и кодом 75, у каждого лимит памяти 4 ГБ — больше, и проход серверов гасит его с причиной «память»; dev-ключи — из `STATE/outside/env/<owner>__<repo>.env` окружением процесса, `.env*`
  дерева закрыт; сам гаснет через 30 минут, не больше 120; `pantheon outside stop ID` — раньше, из любого окна, ждёт
  итога, на чужой ID — «нет такой заявки»; сбой прохода посреди заявки — итог failed и копия снята, копию без сервера
  старше 10 минут проход серверов снимает сам). Повторный `test` на тот же HEAD и ту же папку, пока прежняя заявка в
  очереди или идёт, новой не подаёт — печатает ID прежней и с `--wait` ждёт её; `stop` снимает тест из очереди окна
  (metis-0706). Заявка — в кэш окна, исполняют два прохода со своими замками: тесты
  (`outside run`) и серверы с надзором за ними (`outside run --serve`, «стоп» и срок — за секунды, тестов не ждёт); зовёт их
  только плановый проход. Всё — под `sandbox-exec` с профилем: без чтения ключей (`.env*`, `secrets/`, `STATE/outside/env`, `~/.ssh`, `~/.npmrc`, пароль
  демона CDP, Связка ключей), без записи в состояние, ядро, `~/.claude`, `~/.nvm` и кэши окон и без сети к портам
  браузеров (9222, 9333–9339) и местного прокси (6152, 6153); окружение с нуля. Только папки реестра (`domains.json`): окну — папки своего направления, мастерской — отказ.
  Опора — клон реестра, а не папка роли (metis-0614): `.git`-файл папки разбирается без git и принимается, только если
  ведёт в `<клон>/.git/worktrees/<имя>` клона из папок окна. Клон, его `.git` и gitdir проверяются один раз, в том
  числе самим git; у `.git` клона нет своего `commondir`, а `config` — обычный файл. Дальше git заявки идёт только через
  них (`--git-dir`/`--work-tree`), и `.git`-файл папки больше не читается. Конфиг клона с `include*`, `filter.*`,
  `extensions.worktreeConfig`, командой в `core.fsmonitor` или ключом-командой (`*.command`, `*.textconv`, `*.driver`,
  `*.helper`, `*.program`, `pager.*`, `alias.*`) — отказ; git прохода — с `core.fsmonitor=false`, без хуков,
  сети и подмодулей (`status --ignore-submodules=all`: конфиг подмодуля в `<клон>/.git/modules/` окну открыт), копия —
  через `--git-dir` клона без `~/.gitconfig`. Файл
  ключей — по `origin` клона, а клон — только из папок окна заявки; другие remote ключей не дают. Остаток: ключи сервера лежат в окружении его процесса, а процесс того же пользователя читает его
  (`sysctl KERN_PROCARGS2`, как `ps -E`). `(deny process-info* (target others))` и запрет `sysctl-read` по имени этого
  не закрывают (проба 01.11 на Darwin 25), поэтому серверу — только dev-ключи. Остаток того же рода: роль пишет
  `<клон>/.git/worktrees/<имя>/` (окну закрыты только `.git/config` и `.git/hooks`) и между проверкой и git теста может
  переписать там `commondir`. Это намеренный обход, а не ошибка агента, и граница здесь — песочница (модель угроз —
  README guard). Разбор не наращивается.
  Автопрогонов нет (решение владельца 03.11): после «принять» argus проход тесты сам не гоняет — заявку на итоговый head
  подаёт роль. Проход лишь тревожит дежурного: «принять» без записи tests дольше часа на head, который ещё открыт у PR,
  — одна тревога на (repo, SHA) с номером PR. Запись tests шлюза слияния (`by.agent_type` = `pantheon-outside`) пишет
  проход по заявке: роль её не напишет — STATE ей закрыт, команде под профилем тоже.
  Запись даёт только проверка проекта: с `--script` и у сервера её нет; команда видна в записи (у скрипта package.json —
  с телом), остаток — README guard. Итоги заявок в папках заявок старше суток проход удаляет сам. Роли dev-*, talos,
  лиды и argus называют `pantheon outside test --wait 590` и `pantheon outside serve --wait 120` в своих правилах;
  Stop разработчика засчитывает `pantheon outside test --wait N` как прогон проверки. Подробности — в шапке модуля.
  Дозапуск после красного полного набора (metis-0735). Каждый прогон полного набора (`FULL_TESTS`) проход пишет
  строкой в `STATE/outside/full.jsonl`: `rid` (id заявки), `repo`, `sha`, `tree`, `branch`, `dir`, `cmd`, `env`, `code`
  и `failed` — метки упавших файлов из строк `FAIL плагин/test_x.py` вывода `run-tests.py` (итог не разобран — `null`).
  Красный прогон в журнал шлюза не идёт: там любая запись `tests` значит «прошли». Следующая заявка полного набора на
  той же ветке гонит `<команда> --only <файлы>`: упавшие в последнем полном прогоне ветки и затронутые диффом его
  коммит → HEAD по карте `affected-map.json`. Зелёный дозапуск пишет запись `tests` шлюза с той же `cmd` полного набора
  и полями `rerun_of` (id заявки полного прогона-опоры, всегда настоящего полного, не дозапуска), `files` (прогнанные
  метки) и `map` (sha256 карты на HEAD). Весь набор вместо дозапуска — если дифф задевает файл вне карты, раннер,
  карту, `bin/heavy`, `tests/_*.py` или `.pantheon-verify`, карта устарела, опоры нет, она зелёная, без списка
  упавших или с другой `cmd`/`env`, упавших больше половины, опоре больше суток (`RERUN_MAX_AGE`). Остаток: `test_hash` раннера читает файл тестов без
  предела размера (и по ссылке), так что файл-гигант растит память прохода. Список условий и разбор — шапка `outside.py`.
- `plugins/pantheon/lib/read.py` — чтение переписки по заявке с согласием владельца (metis-0267, 0508, 0385):
  `pantheon read request --direction D (--folder ИМЯ | --chat id/@имя/ссылка/название)… --since --until --why`.
  Чаты по указаниям находит плановый проход (`read run`, без модели) через источник-надстройку: путь к исполняемому
  файлу и имя субагента-читателя — таблица `[read]` в `STATE/config.toml` (пишет владелец), контракт глаголов
  resolve, export и verify — в шапке модуля. Мессенджера и скрипта в ядре нет: без `[read]` — «источников чтения
  нет». В вопросе `[read-<rid>]` — id найденных чатов с числом сообщений и путь к `list.md` заявки: названия чатов
  от источника (чужой текст) лежат только там, в файле с шапкой выгрузки, а в карточки Зевса, state и журнал не идут.
  У отказа «подходит несколько» в карточке только число, путь к `candidates.md` владелец получает уведомлением. Хеш
  согласия покрывает и заявку, и список чатов с названиями. Пределы на заявку — 92 дня, 100 чатов, 10 000 сообщений

  обрезки). Столько один читатель не держит, поэтому выгрузка читается частями по 120 000 знаков (≈ 60 тыс. токенов):
  по читателю на часть, большой чат режется по сообщениям, части идут несколькими проходами (этап reading, не
  дольше 24 ч). Разбор — один на заявку: пункты всех частей сводятся в один список, пункт ссылается на чат своей части
  («чат K, #id»), цитату проверяет verify по выгрузке этого чата. Тест — `plugins/pantheon/tests/test_read.py`
  (поддельный источник: папка, список, смесь, пустая папка, неизвестное имя, большая выгрузка частями).
- `plugins/pantheon/hooks/dev-stop-verify.py` — Stop разработчика (в шапке ролей dev-*): красная проверка проекта

  при любой правке, а его чтения в связи файлов не идут, поэтому правка, например, `bin/heavy` даёт только тесты,
  которые heavy запускают (metis-0791). В карте — sha256 каждого файла тестов: раннер находит файлы, изменённые после
  сборки, и гонит их при любом изменении (их связи по карте могли устареть); таких 8 и больше — весь набор с
  причиной в выводе. Карту строят заново, когда таких файлов набралось; то, что устаревшая карта пропустила, ловит
  полный прогон на main.
