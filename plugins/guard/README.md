# guard

Правила, которые Claude Code проверяет сам, а не на память модели. Хук PreToolUse (Bash, Write, Edit, MultiEdit,
NotebookEdit, Read, Grep, Glob, WebFetch, Agent, Task, Skill) и Stop; хуки зовут короткий вход `hooks/guard.py`,
правила — модуль `hooks/guard_rules.py`, его шапка их перечисляет (metis-0148). Флаг «сессия читала сырой Telegram» — отдельный `hooks/taint.py` (раздел tg-taint).

## От чего защищает (модель угроз, SEC-27, [sb-simplify] 27.10)

1. Ущерб — пять видов: ключи; браузер со входами владельца; main и ядро без ревью; действия наружу; удаление данных.
2. Правило guard остаётся, только если называет ущерб из пяти: зоны записи по направлениям и запрет dev-сервера сняты.
3. Граница — песочница macOS окна роли (`pantheon domains build`) и управляемые настройки `managed-settings.json`.
4. guard — защита от ошибок агента, а не от намеренного обхода: что делает программа изнутри, он не видит.
5. Находка проверки безопасности — «ошибка агента или граница песочницы»; намеренный обход — в остатки, не в новый круг.

### Остатки — что guard не держит и так задумано

- **Программа изнутри.** `python3 -c "…os.system(base64.b64decode(…))"`, `node -e`, `make`, скрипты: guard видит только
  строку команды. Держит песочница окна; разбор Bash ради новых обходов не наращиваем (решение 19.10).
- **launchd-env.** Копия `/bin/launchctl` под другим именем (`cp /bin/launchctl ./lc && ./lc setenv …`), код из stdin или
  подстановки (`. /dev/stdin <<< '…'`, `source <(…)`), имя глобом (`/bin/launchc?l`) или по частям (`$(echo launch)ctl`,
  `read L <<< launch; ${L}ctl`) — ревью 84d пп. 3–4, 84f пп. 2–3. Имя из переменной, которую разбор вычисляет
  (`L=launch; ${L}ctl`), guard ловит.
- **Чтение `.env` и `secrets/`** держат правила `Read(.env)`, `Read(.env.local)`, `Read(.env.*.local)`, `Read(secrets/**)`
  в managed-settings.json: Claude Code вливает их в denyRead песочницы (тест — `test_canaries.py`).
- **Grep Пританея по `.git`** держит только песочница.
- **Задачи чужого направления** (решение 28.10, п. 4). Роль может вести задачи другого направления через `pantheon task`: проверка `task_targets` снята. Доску и owner-log пишет только плановый проход, «да» владельца — только owner-log.
- **Ключи демона Claude Code** (решение 28.10, metis-0287). `~/.claude/daemon` (roster.json, control.key) окнам ролей открыт: с ключами PTY можно напечатать текст в фоновую сессию, в том числе в окно Пританея, и owner-log может принять его за ввод владельца. Только намеренно или по внедрённой просьбе; владелец счёл риск малым.
- **Edit/Write песочница не держит.** Их судят protect-config (профили оболочки, `~/.ssh`, настройки git, LaunchAgents,
  `~/.claude.json`, `~/.local/bin`, защиты в `~/.claude`), pantheon-acl, private и domain (остальное в `~/.*` и
  `~/Library`). Сессии владельца без роли domain не ограничивает.
- **gh мимо песочницы в окне направления** (gh-out, metis-0533): `gh pr create|edit|comment|ready` идут вне песочницы
  (GH_PR_WRITE), правило пускает их только с `-R` из `[merge_repos]` своего направления (окно — по PANTHEON_WINDOW),
  без `--hostname` и адреса PR, а `--body-file`/`-F` — только realpath внутри временных папок и своей копии
  репозитория. Каждый `-R` (и склеенный `-Rx`, `--repo=x`) сверяется со списком. Из файла не уходят личное
  (`[private] paths`) и всё под `.git` любой копии — ключ git-crypt, `config` (metis-0596: в окне mnemo-brain своя
  копия — `~/ai/knowledge` с `me/`, а главную сессию check_private не судит); шаблон оболочки в имени файла — отказ.
  Относительный путь файла — только когда в строке одна команда, сам gh: в строке из нескольких команд (`cd docs &&`,
  подоболочка, `;`, конвейер, `sh -c '…'`) и при вызове gh через любую обёртку (`env`, `sudo`, `uv --directory`,
  `pnpm -C`, `nice` …) — отказ с подсказкой «дай абсолютный путь»: ни имена команд, ни опции обёрток не разбираем. `env` с любой длинной опцией (`--…`) или с `S` среди коротких
  (`-S`, `-iS`) в строке с gh — отказ: строку `-S` env разбирает сам, сокращения не перебираем.
  `GH_*`: «GH_X=» где угодно в строке — отказ: перед командой (`GH_REPO=x gh …`, в том числе внутри `sh -c '…'`), в
  словах обёртки (`env "GH_HOST"=h`, `env GH_HOST\=h` — по разобранным словам), в соседней команде и в значении флага
  gh; `export`/`declare`/`read GH_*` и они же с невычислимым словом (`export $X`, `read $V`) — тоже. Слово `GH_TOKEN` без «=» — не отказ. Ложный отказ на `--body 'set
  GH_TOKEN=x'` и `-t 'GH_HOST=h'` оставлен намеренно: сверка сырого текста с разобранными словами — два разных
  разбора, она давала обход (`GH_HOST=x gh … --body=GH_HOST=x`); такой текст — в `--body-file`. `$` в двойных
  кавычках (`--body "cost $5"`) — подстановка, её не вычислить, поэтому отказ: буквально
  — в одинарных кавычках или `\$`. `--recover` в таблице нет: gh читает им любой файл. Окно, чья папка запуска содержит личное (`[private] paths`; mnemo-brain: главная сессия, координатор и субагент), через
  gh pr create|edit|comment|ready и merge (все формы GH_PR_WRITE) не публикует вовсе, с любым текстом и файлом — тот же признак, что у правила push
  (SEC-13, metis-0600): оно видит `me/` и выписки из веба, третье свойство (наружу) ему не даём. PR и комментарий
  открывают лид или владелец. Остальные gh (issue, release, api, alias, extension) мимо песочницы не идут — в ней gh не работает; `gh api` с записью закрыт ещё правилом push. metis и роли продуктов — без изменений. Остаток: текст самого комментария (`--body`) и файл внутри своей копии уходят на GitHub как есть;
  `gh repo set-default` и `.git/config` подменяют целевой репозиторий только без `-R`, а он обязателен; `gh alias`,
  `gh extension`, `gh api` в песочнице и мимо неё не идут. Форма, где имя gh скрыто (`env -S 'g''h …'`, `$X pr comment`), не ловится: она не совпадает с excludedCommands, уходит в песочницу, а там gh не работает (намеренный обход). Ещё остаток: файл, который проверен, подменяют между проверкой и запуском — симлинком или записью другой командой в той же
  строке (TOCTOU). Флаги формы — по таблице (`GH_OUT_*` в guard_rules.py): неизвестный флаг, флаг gh до `pr` кроме `-R`,
  значение `-R`/`-F`/`--body-file` на «-» и копия репозитория без `.git` (или корень `$HOME`) — отказ. Намеренный обход — граница песочницы, разбор Bash не растёт.
- **Подмена `.git/config` и симлинка cwd** между «можно» guard и запуском команды — намеренный обход, граница — песочница
  окна (разделы «Окно Пританея» и «Слияние PR», «Пределы»).
- **Браузер через свой скрипт.** cdp-role смотрит весь текст команды Bash; запуск своего скрипта, который сам
  читает пароль демона и ходит на его порт (`python3 sites.py`, `pnpm test`), не отличить от любого запуска — читать
  каждый скрипт guard не стал бы: тесты с этими строками как данными тоже закрылись бы. Такой запуск держит окно роли:
  местных портов у песочницы нет, папка пароля закрыта denyRead и `Read(~/.config/cdp-daemon/**)`. Порт и имя демона,
  собранные по частям (`"93"+"33"`, переменная из файла), — намеренный обход, граница та же; такие находки идут сюда,
  без нового круга правок (metis-0624). Обратная сторона: слова в тексте вне исключения — `echo … > заметка.md`,
  `grep 9333 sites.py`, heredoc в `git commit -F -` — по-прежнему отказ; заметку пишут Write, сообщение — `-m` или `-F файл.md`.
  Исключение действует, только когда первое слово команды — ровно `git`, `gh` или `pantheon` (metis-0630): присваивание,
  обёртка (`env`, `time`, `exec`, `!`, `(`, `{`) или путь к команде перед ним снимают его, и правило смотрит весь текст.
  Другие найденные способы спрятать окружение команды за этим исключением — тоже намеренный обход: они идут в этот
  остаток, без нового круга правок разбора.
- **Браузер по адресу.** cdp-role ловит по номеру порта, а не по записи адреса; у WebFetch — ещё имена вроде
  `localtest.me` и `nip.io`. При местном прокси с подменой адресов имена разрешаются в 198.18/15, и настоящий адрес не
  виден — это предел правила.
- **Запись `tests` из файлов, которые меняет сам PR** (`.pantheon-verify` ветки, скрипт test в package.json), и
  настоящесть команды тестов — на argus: он сверяет поле `cmd` (раздел «Слияние PR», «Пределы»).
- **`pantheon outside`** — профиль «разрешено всё, кроме списка»: чтение папок других направлений и прочая сеть
  открыты. `~/.npmrc` закрыт на чтение (npm и pnpm без него работают — проба 28.10): проект, которому ключ частного
  реестра нужен из `~/.npmrc`, вне окна зависимости не поставит — ставь их в окне (`heavy pnpm install`).

### Что ловит

guard ловит **ошибки агента**: запись чужой памяти ролей и Edit/Write в `~/.*` и `~/Library` мимо protect-config (domain), правку чужого файла Пританея, файла задачи
мимо `pantheon task` и доски или журнала ваших слов любой сессией Claude (pantheon-acl), пульт (кроме запуска окон), `pantheon approve` и `pantheon merge run` ролью, правку защит не той ролью (protect-config), чтение ключей
(tg-secret; ролям из демона tg-readd — только `status` и `kickstart`), пометки об авторстве Claude; с шага 1.2 — по ролям Пантеона: личное (private: `me/`,
ключи git-crypt, журнал Пританея — только hq, chiron в окне Пританея и mnemo-brain; ключи — никому из ролей), Telegram
и коуча chiron вне своего окна, Гестию субагентом и вне её окна, gh pr окна Пританея не по своему репозиторию (hq-telegram, chiron, hestia, hq-gh — раздел «Окно Пританея»), выгрузку личного чата Telegram в окне любой роли (tg-role), браузер владельца
(cdp-role: демон — никому из ролей, браузеры владельца — у Харона после metis-0077; прямой отладочный порт и WebFetch на локальные адреса —
никому; по всему тексту команды Bash — порт демона 9333–9339 и слово `cdp-daemon` (с ним и папка пароля `~/.config/cdp-daemon`), прямой порт браузера 9222, `DevToolsActivePort`, `/devtools/browser|page/` и `remote-debugging`; исключение (metis-0624) — эти слова только в значении флага-сообщения у одной простой команды без `;`, `&&`, `|`, `$(…)`, перенаправлений (`2>&1` тоже) и первым словом ровно `git`, `gh` или `pantheon` — без присваивания, обёртки и пути перед ним (`GH_HOST=… gh`, `env X=… git`, `time`, `exec`, `/usr/bin/git` — metis-0630): `git commit -m/--message/-F/--file файл.md`, `gh pr|issue create|edit|comment -b/--body/-t/--title/-F/--body-file файл.md`, `pantheon task new|set --text/--note/--title…` и `поле=текст` (result, note, title…) в task new|set; позиционный заголовок `pantheon task new "…"` в исключение не входит — заголовок через `--title`; отказ Bash подсказывает это исключение; Read, Grep и Glob папки пароля — отказ; Edit и Write исходников с этими словами правило не смотрит; ловит по номеру порта, а не по записи адреса; у WebFetch — ещё имена вроде localtest.me и nip.io, а при прокси с подменой
адресов имена разрешаются в 198.18/15 и настоящий адрес не виден — это предел правила), push (только в свою ветку, не в main/master, без force — в том
числе `+ветка` — и удаления; `gh api` с записью — нет; `gh pr merge` — только главная сессия координатора или его лид в папках своего направления, защиты — только Метида или её лид; везде — через шлюз слияния: тесты, «принять» от argus и `--match-head-commit` на один SHA, подробно — раздел «Слияние PR»; координатор с личным в папке — mnemo-brain —
не отправляет и не сливает сам; отправляют только свой репозиторий — папки своего направления), печать в терминал (terminal: osascript, tmux
send-keys и т. п. — ввод от имени владельца), пополнение корпуса (corpus-role: подкоманды, скрипты и ключи в Связке — по списку из раздела `[corpus]` policy.toml,
образец — в `policy.example.toml`; ни одной роли, только через посредника; Пританею корпус закрыт целиком; раздела нет или все его списки пусты — правило ничего не узнаёт, а при корпусе, объявленном в `[hq]`, плановый проход тревожит: «нет раздела [corpus] или он пуст», metis-0194; битый раздел — ролям Bash закрыт), launchd (launchd-env, metis-0298: ролям, субагентам и главной сессии окна роли (`PANTHEON_ROLE` задан, agent_type в событии нет) `launchctl` — только белый список для чтения: list, print, print-cache, print-disabled, getenv, blame, version, help, procinfo, hostinfo, managerpid, manageruid, managername; остальное — setenv, unsetenv, config, bootstrap, bootout, load, unload, submit, remove, kickstart, enable, disable, обёртки asuser и bsexec, вызов без подкоманды и неизвестное — отказ: окружение и службы launchd берёт плановый проход Пантеона; имя переменной и метка не важны; `swiftc` — только абсолютным `/usr/bin/swiftc`, путь сверяется у слова каждой команды (metis-0314); launchctl внутри `python3 -c`, `perl -e` и скриптов — ниже модели угроз, guard его не видит, как и launchctl внутри `pantheon` и `tg-readd`).

Узкие роли и защиты проекта:

- **momus** (ревизор) пишет только в `agent_extra` своей роли из policy.toml, свою память и временные папки — корней по папке запуска
  или git-репозиторию у неё нет (`EXTRA_ONLY_ROLES`), а новый файл в чужой `inbox/` направления ей закрыт; без policy.toml — только память и временное.
- **momus без agent_id** (главная сессия `--agent momus`) получает те же границы, что momus-субагент (guard 0.5.10, metis-0177).
- **palamedes** (исполнитель без кода, `DRAFT_ONLY_ROLES`, metis-0469) пишет только черновики: Write, Edit, MultiEdit в
  `~/ai/pantheon/directions/<своё направление>/drafts/**` (направление — по папке запуска окна), из окна Пританея
  (`PANTHEON_ROLE=hq`) — в `drafts/` любого направления из domains.json. Закрыто: код проектов, свой и чужой `STATUS.md`,
  планы и другие файлы направления, любые `inbox/`, `~/ai/knowledge`, `~/.claude`, память, временные папки; `agent_extra`
  из policy.toml для неё не действует. Пути сравниваются после realpath и без регистра (macOS): `drafts/../STATUS.md` и
  симлинк из `drafts/` наружу — отказ. Правило draft-role: из инструментов, которые видит guard, ей открыты только Read,
  Grep, Glob и эти три — Bash, NotebookEdit, WebFetch, Agent, Task и Skill закрыты (MCP и WebSearch закрывает список
  `tools:` в шапке роли). Главная сессия `--agent palamedes` (без agent_id) — те же границы.
- **protect-config** защищает и саму папку `<репо>/.claude` как цель записи (`cp -R x <репо>/.claude/`, `mv`, `tar -C`, `rsync`):
  в неё можно положить settings.json и agents. Вложенное (`.claude/worktrees/…`) правилом не закрыто. С guard 0.5.10 (metis-0177):
  - `hooks/`, `skills/` и `commands/` проекта (`<репо>/.claude/…`, и в worktree) закрыты, как `agents/`;
  - закрыта и цель выше `.claude` — сам репозиторий или папка над репозиториями, если туда ложится дерево с любыми именами:
    распаковка (`tar -x`, `unzip`, `ditto -x`), `cp -R`/`-a`, `ditto`, `scp -r`, `rsync -r`/`-a` или с источником `папка/`;
    `git clone` в `<репо>/.claude` тоже закрыт;
  - файлы с известными именами в корне репозитория можно: `curl -O`, `wget`, `patch -p1 -i x.diff`, `rsync a.txt .`, `cp a.txt .`;
  - с metis-0194 закрыты ещё: `rsync` с источником `папка/.` или `.`, с `-R`/`--relative`/`--files-from` (они кладут
    `.claude/…` как путь), опция после операндов (`rsync -a src/ . --exclude x`); `wget -r`/`-m` (сайт кладёт дерево
    с путями из адреса; папка — `-P` или cwd); `7z x|e -o<папка>`; `git checkout`/`git restore` с путём `.claude/…` или
    самой `.claude` (`--staged` — только индекс, не судим; `.` и папка репозитория — можно: возвращают только то, что уже
    в git, как `reset --hard`); `unzip -d` в `.claude`. `unzip -l/-t/-Z/-v/-p` и
    `7z a` ничего не пишут и не отказ. После `cd` (`cd <репо> && 7z x a.7z`, `wget -m`) относительную папку судим
    от каждой папки cd и от папки события: `cd app && 7z x a.7z` из корня репозитория — тоже
    отказ. Источник rsync `.`, `..`, `папка/..` — тоже дерево (`rsync -d . <репо>`);
  - остаток: опции rsync со значением отдельным словом, которых нет в `RSYNC_VALUE_OPTS` (`--compress-level 9`,
    `--max-delete 5`), читаются как операнд: `rsync -a src/ . --compress-level 9` даёт ложную цель «9» и проходит.
    Слитная форма (`--compress-level=9`) судится верно. Не наращиваем: защита от ошибки, а не от обхода;
  - пустую папку `.claude` можно создать (`mkdir`, `install -d`), `install -d .claude/agents` — нет.
- **`[private]` в policy.toml:** не таблица — всё по умолчанию; ключа нет или значение не список — умолчание; список — только его
  строки (без пробелов по краям, пустые и не строки отброшены). `roles` и `coordinators` пустым списком `[]` — никого.
  `paths` пустым списком `[]` или из одних пустых строк — умолчание: личное остаётся закрытым, опечатка его не открывает
  (guard 0.5.10, ревью PR #35). Шлюз слияния читает `[]` так же и его пропускает (для `paths` — умолчание), а на неверном
  `[private]` (не список, не строки) закрыт: опечатка не открывает слияние.

Песочницу macOS в окнах ролей (SEC-19, SEC-26) собирает `pantheon domains build` в
`~/.local/state/pantheon/settings/<направление>.json`; управляемые настройки (SEC-28) — главные запреты и хук guard,
которые не перебить настройками проекта и модами (раздел «Управляемые настройки»).

## Режимы и поведение при сбое (SEC-10, SEC-29)

| Запуск | Кто вызывает | Особенность |
| --- | --- | --- |
| без аргумента | хук этого плагина | если guard уже вызывают управляемые настройки (`--managed`), хук плагина молчит — кроме Agent, Task и Skill |
| `--managed` | хук из управляемых настроек | — |
| `--strict` | хук окна роли с `onFailure: "block"` | таймаут или пропавший файл останавливают и на старом Claude Code |

**Правила из .pyc и меньше лишних проверок (metis-0148).** Хуки зовут короткий вход `hooks/guard.py`: он читает
событие и решает, молчать ли хуку плагина, не загружая правил, а правила грузит модулем `guard_rules.py` из
`hooks/__pycache__` (.pyc) — компиляция 4000 строк была больше половины времени вызова. Молчит только хук плагина;
управляемая копия (`--managed`) и строгая (`--strict`) проверяют всегда — управляемую ничто в файлах не выключает.
Хук плагина молчит:
- при управляемых настройках с `guard.py --managed` — как раньше, кроме Agent, Task и Skill;
- в окне роли — на инструменте, который строгий guard этой же сессии уже проверил (так и Agent, Task, Skill). Строгий
  guard на PreToolUse пишет метку `~/.local/state/pantheon/guard-strict/<session_id>`, строка «окно, табуляция,
  инструмент», и обновляет её на каждом вызове. Хук плагина молчит, только если в метке есть его окно
  (`PANTHEON_WINDOW`) и инструмент, а метка свежее 10 минут. Первый вызов инструмента в сессии проверяют все копии.
  Ваша сессия, вложенный `claude` и `claude -r` без окна своей метки не имеют. Метку не прочесть или не записать
  (ссылка, папка, нет места) — полная проверка, как раньше. Метки старше 2 суток убирает строгий guard, когда
  создаёт новую.

В окне роли с управляемыми настройками на вызов идут две полные проверки (управляемая и строгая) и один быстрый
выход хука плагина; каждая полная — из .pyc.

**Любой сбой — выход 2 с причиной в stderr, во всех трёх режимах и в вашей сессии тоже** (metis-0094, guard 0.5.5).
Сбой — событие не JSON или не объект, исключение в проверке прав (domain, pantheon-acl, protect-config, private,
cdp-role, push, terminal, hq-telegram, tg-role, chiron, hestia) или tg-secret, сбой всего скрипта, свой срок 8 с (таймаут хука —
10 с, а таймаут Claude Code вызов пропускает). Код 2 Claude Code понимает как блок на любой версии. Второй слой
(guard 0.5.6, metis-0094) — `"onFailure": "block"` у обработчиков PreToolUse guard и pantheon в hooks.json (Claude
Code 2.1.295+): таймаут, выход не 0 и не 2 или незапуск хука тоже блокируют вызов (проверено вживую на 2.1.301). У
maint-pre pantheon это значит: сбой ctx.py при maintenance.json закрывает инструменты до снятия обслуживания. Как это сделано — обёртка `run_hook` в
`guard_rules.py`, образец — `plugins/pantheon/hooks/agents.py`.

| Событие | Код 2 в Claude Code | Сбой guard |
| --- | --- | --- |
| PreToolUse | блок вызова, причина — агенту | выход 2 |
| PostToolUse (журнал шлюза слияния) | команда уже выполнена, причина — агенту | выход 2: агент узнаёт, что запись не сделана |
| Stop (подсказка nextjs) | ход не заканчивается | выход 0 и строка в журнале: код 2 крутил бы сессию без конца |

Правила-подсказки (dev-server, attribution, cdp, nextjs) при сбое пропускают к остальным проверкам: это подсказки,
а не защита. Каждый сбой — строка в
`~/.local/state/pantheon/logs/guard-failures.log` (время, режим, место, тип ошибки; без текста команды),
строка статуса показывает число сбоев за сутки.

## Ответ владельца не подделать мимо журнала (metis-0044, guard 0.5.1)

Ответ на карточке доски подтверждает только журнал ваших слов `~/.local/state/pantheon/owner-log/`: его пишут хук
answer и плановый проход, это скрипты, guard их не видит. Сессия Claude вписать ответ не может ни одним из двух путей.

- **Доска и журнал.** В `~/ai/pantheon-view` (доска Obsidian: карточки, галочки, заметки) и в `owner-log/` не пишет
  ни одна сессия Claude: ни роль, ни субагент, ни ваша обычная сессия без роли. Доску вы правите в Obsidian сам.
  У сессии без роли запрет — по явным целям Edit, Write и Bash внутри этих двух папок. Цель, которую разбор Bash не
  вычислит, и запись в папку выше (`cp a ~/` даёт цель `~`) ей не запрещены, иначе встали бы обычные команды. Остальной
  `~/.local/state/pantheon` сессии без роли открыт, как раньше: ответа там нет.
- **Файлы задач.** `~/ai/pantheon/directions/*/tasks/` и входящие `~/ai/pantheon/inbox/tasks/` роли и любые
  субагенты, Пританей тоже, меняют только командой `pantheon task` (new, set, claim, split). Команда не принимает поля `answer`
  и `requested`: их ставит плановый проход из журнала. Прямая правка (Edit, Write, перенаправление, `cp`, `mv`, `rm`) — отказ.
  Запись в папку над `tasks/` целиком — тоже отказ: `cp -R`, `rsync`, `tar -C`, `unzip -d` или `cp a.md` в
  `directions/<имя>/`, в `directions/` или в `inbox/` положили бы в `tasks/` что угодно. Файл туда копируют с
  точным именем: `cp a.md directions/<имя>/a.md`. Удалить или переименовать папку направления целиком (`rm -rf`,
  `mv directions/<имя>`) роли тоже не могут: это делает ваша сессия без роли или `pantheon archive`. Можно создать новую папку направления, ещё не существующую папку
  `tasks/` и заглушку `.gitkeep` или `.keep` в ней (пустую папку плановый проход в git не положит): ответа в них нет. Ваши сессии
  без роли файлы задач править могут: доска с pantheon 0.9.27 берёт ответ из журнала, а не из файла.
- **Почему закрыт весь `~/ai/pantheon-view`, а не только `Доска/`.** Остальная копия и так только для чтения
  (`view-sync.sh` снимает права на запись). Настройки Obsidian в `.obsidian/` копия не трогает, и их теперь тоже не
  правит ни одна сессия Claude: меняйте их в самом Obsidian.

## Окно Пританея: Telegram, chiron, пульт, ключи (guard 0.5.5)

Роль окна guard берёт из переменной `PANTHEON_ROLE`: её ставит `pantheon start` в файле окна, роли его не перепишут.
В событиях фоновой сессии `agent_type` нет, а у субагента он свой, поэтому «это окно Пританея» по событию не узнать.

- **hq-telegram (P0-1, metis-0060).** В окне Пританея (`PANTHEON_ROLE=hq`) отказ: субагент `tg-reader`, навык
  `telegram-read` (и `плагин:telegram-read`), Bash со скриптом tg-read или демоном `tg-readd` в тексте команды. Причина:
  у Зевса личное и действия наружу, а переписка и каналы — чужой текст. Вопросы по Telegram-каналам — Фемиде
  (направление источников) через поручение. Рядом то же закрывают хук qmd-query плагина pantheon (коллекции из
  `[hq].closed_collections` policy.toml) и песочница окна (папки из `[hq].closed_dirs`).
- **tg-role (metis-0267, guard 0.5.12).** В окне любой роли (`PANTHEON_ROLE` задан, вместе с её субагентами) отказ на
  Bash `tg_read.py history|search|unread|context|download` и на сокет `tg-readd.sock`: выгрузка личного чата — через
  `pantheon read request`. `posts`, `status`, `chats`, `folders`, `verify` и `split` можно. Процесс без `PANTHEON_ROLE`
  (плановый проход, ваша сессия) правило не трогает. Команды — из общего разбора Bash, как у tg-readd: переменные
  (`T=…; $T history`), перенос `\`, `--`, `sh -c`, `env`, `uv run`, `xargs`, имя без учёта регистра и шаблоном;
  подкоманду не вычислить — отказ. `python -m`, сокет из своего кода и `env -u PANTHEON_ROLE` — граница песочницы.
- **chiron (P0-2, metis-0061).** Коуч видит личное, только когда `PANTHEON_ROLE=hq`. Позвать его (Agent или Task с
  `subagent_type: chiron`) можно в окне Пританея и в вашей сессии без роли; из окна другой роли и из субагента вне окна
  Пританея — отказ.
- **hestia (metis-0245, guard 0.5.18).** Гестия пересобирает и перезапускает окна командами пульта, поэтому её
  граница — своё окно песочницы (`settings/hestia.json`, `PANTHEON_ROLE=hestia`; поднимает `pantheon wake hestia --task
  <id>`). Субагентом (Agent или Task с `subagent_type: hestia`) её не зовут нигде, и в вашей сессии тоже: субагент шёл бы
  с правами позвавшего. Роль hestia вне своего окна — отказ любому инструменту. В окне главная сессия фоновая и
  agent_type у неё нет, поэтому правило смотрит на окно. В нём Edit, Write, MultiEdit и NotebookEdit — отказ; Bash пишет
  только во временные папки (TMPDIR, /tmp); git — только чтение по белому списку (`status`, `log`, `show`, `diff` и
  т. п.), любая запись в любой форме (`git -c … commit`, `git -C … push`, `tag`, `reset`) — отказ; `gh` — только `pr
  view|list|diff|checks|status` и `gh api` без записи; `claude` — только `plugin list`, `agents`, `--version` (выпуск
  ставит `pantheon plugins update`, голый `claude plugin update` — отказ); пульт — только `plugins update`, `domains
  build`, `restart` без `--force`, `alert`, `task show`, `status`, `who`, `agents`, `consent`, `reap` (виновники памяти,
  metis-0568: гасит сама команда и только брошенное в папках Пантеона, по `--pid` — только pid из вопроса о гашении
  с «да» владельца: метка `<id>.reap`, push и PR она не открывает), и через
  оболочку или python по пути тоже. Имя команды или подкоманду не вычислить (`$X`, `$(…)`) — отказ.
  Наружу (metis-0562, «Да, по consent» владельца 27.10): сети у песочницы окна нет; мимо неё идут только `git push` и
  `gh pr create|edit`, и только при свежей (до 2 ч) метке задачи окна в `<state>/hestia-consent/<id>`. Метку ставит
  `pantheon consent <id>`, запущенный в окне hestia, и только на явное «да» владельца в окне вопросов; id должен
  совпасть с `PANTHEON_TASK` окна (его задаёт `wake hestia --task`), метка другой задачи, папка, ссылка и старше 2 ч не
  считаются. Куда: push — только на имя remote (не адрес), без main, force и удаления ветки (правило push); `gh pr
  create|edit` — только с явным `-R` из `[merge_repos]` направления задачи (`PANTHEON_TASK_DIRECTION`), без `GH_*`, и
  `--body-file`/`-F` только из временных папок. Рядом с push другая команда в строке (`git push && rm …`) отключает
  пропуск проверки записи: он действует лишь для строки из одних `git push`. Опции push — белый список: `-u`,
  `--set-upstream`, `--force-with-lease` (без значения или `=ветка`); перед push у git опций нет (`-C`, `-c`,
  `--git-dir`, `--work-tree`); сокращения длинных опций (`--rec`) тоже отказ. Остаток: защита от ошибки, не от
  намеренной подмены .git/config (модель угроз README guard). Слияние, `gh api` с записью, `curl`, `ssh`
  и `git fetch|pull|clone|ls-remote` не открываются и с меткой.
- **hq-gh (metis-0247, guard 0.5.13).** Окну Пританея gh pr view, checks, list и edit выпущены мимо песочницы, а у
  Зевса личное. Поэтому в этом окне любой `gh pr` проходит только с явным `-R`/`--repo` из `[merge_repos]` policy.toml
  и номером PR; без `-R`, с любой `GH_*` в команде или с `GH_REPO`, `GH_HOST`, `GH_CONFIG_DIR` в окружении, с `--comments`/`-c` и `--json comments`
  (и `reviews`, `latestReviews`) — отказ.
  `gh pr list` (metis-0626) — тоже только с `-R` из `[merge_repos]`, но без номера и вообще без позиционных слов, и
  только с флагами `--state`/`-s`, `--limit`/`-L`, `--base`/`-B`, `--head`/`-H`, `--label`/`-l`, `--author`/`-A`,
  `--assignee`/`-a`, `--json`, `--jq`/`-q`, `--template`/`-t`, `--draft`/`-d`, `--web`/`-w`; длинные со значением —
  и через `=`. `--search`/`-S` — отказ: текст запроса уходит в GitHub. Любой другой флаг (`--app`, `--`) — тоже отказ.
  `gh pr diff` и `gh run` окну Пританея не выпущены: лишний чужой текст в окне. Личный путь в команде (`--body-file`, `-F`, `$(cat …)`, `< файл`, `$(< файл)`) — отказ тем же разбором, что правило private у
  координаторов.
  Слияние окну Пританея закрыто всегда (ревью 69m-b): `gh pr merge` с `-R` и без, а также `gh api` к
  `…/pulls/<N>/merge`, `…/merges` и мутации `mergePullRequest`, `enablePullRequestAutoMerge` — отказ. Шлюз слияния
  берёт роль из agent_type, а у главной сессии окна его нет: без этого отказа она прошла бы мимо шлюза.
- **hq-sessync (metis-0566).** Окну Пританея `sessync find <слова> [-p имя] [-n число]` выпущен мимо песочницы
  (`excludedCommands` окна Пританея, `HQ_EXCLUDED` в pantheon.py): поиск по прошлым разговорам читает транскрипты
  `~/.claude/projects`, закрытые окну, а вывод проходит маску похожего на ключи — она в самом sessync. Правило — одна
  строгая проверка всей сырой строки: `sessync find` и токены, где токен — слово из букв, цифр и `_.-` (не с «-»), то же
  слово в кавычках (внутри ещё пробелы), `-p <имя из a-z0-9_->` или `-n <цифры>`. Всё остальное — отказ: `--raw`,
  `--no-mask` и любой другой флаг, префикс присваивания (`PATH=… sessync find`), `env`, `bash -c`, `;`, `&`, `|`,
  перенаправления, подстановки, глобы (`* ? [ ] { } ~ ^ # !`), перевод строки, путь к команде. Иначе хвост команды или
  раскрытое оболочкой ушли бы мимо песочницы вместе с `find`. Другим окнам `sessync find` мимо песочницы не выпущен.
- **Agent, Task и Skill при управляемых настройках.** Управляемые настройки вызывают guard только для Bash, Write,
  Edit, MultiEdit, NotebookEdit, Read, Grep, Glob и WebFetch. Поэтому эти три инструмента хук плагина проверяет и тогда,
  когда guard уже стоит в управляемых настройках. Сбой этих проверок — отказ.
- **Пульт (metis-0047; решение владельца 28.10, п. 5).** Запуск и перезапуск окон — `pantheon start`, `wake`, `resume`,
  `restart` — ролям открыт: их делают Зевс и плановый проход без «да», границы задаёт сам пульт. Остальной пульт — только Пританей и ваши
  сессии: `archive`, `install`, `uninstall`, `commit`, `stop`, `pause`, `jobs pause|resume|disable|enable|renew`,
  `roles build` (ролям — только `--out <папка> [--src <папка>]` внутри временной папки, п. ниже). `pantheon saved` и
  `pantheon who` открыты всем. `pantheon approve` — только владелец, `pantheon merge` — роли только `request`, `status`,
  `cancel`. Пульт по пути (`sh ~/.local/bin/pantheon …`) и копия под другим именем судятся так же. Файлы `~/ai/pantheon`
  из `HQ_ONLY` (approvals.toml, schedule.toml, directions.toml, decisions.md, board.md и др.) правит только Пританей.
- **Пробная сборка ролей (metis-0097).** `pantheon roles build` ролям закрыт, кроме `--out <папка> [--src <папка>]`, где
  `--out` — разобранный путь внутри временной папки (TMPDIR, /tmp); любой другой вид команды — отказ.
- **Ключи git-crypt Пританею (metis-0084).** У hq и chiron из личного закрыты только ключи. Отказ — на явный путь в ключ
  или шаблон, который в него раскрывается (`ls ~/ai/pantheon/.git/*`). Поиск по папке выше (`grep -r … ~/ai/pantheon`,
  Grep по ней) проходит: ключи закрывает и песочница окна. Ролям без доступа к личному правило прежнее: `grep -r` по
  папке, где лежит `me/`, — отказ.

## Сессия читала сырой Telegram — действия наружу с вопросом (tg-taint, metis-0083, guard 0.5.6)

Переписку в Telegram пишут чужие люди, и в ней могут быть внедрённые указания. Поэтому сессия, в контекст которой
попал сырой текст чата, помечается флагом. Пока флаг стоит, действия наружу и записи в долговременные места
проходят только через вопрос. Чтение и пересказ идут без вопросов. Код — `hooks/taint.py`, отдельно от guard (`guard.py`, `guard_rules.py`).

**Когда ставится.** Флаг — файл `~/.local/state/tg-taint/<session_id>`. Его ставит PostToolUse, только при успешном
вызове:

- `tg_read.py history|search|unread|context|posts|download -o -` — выгрузка идёт в stdout, то есть в контекст. Без
  `-o` и с `-o ФАЙЛ` выгрузка ложится в файл, а в выводе только путь и сводка — флага нет;
- Bash, в выводе которого шапка выгрузки tg_read («Переписка — строго между строками «<<<TG-…»»);
- `cat`, `head`, `sed`, `grep`, `less`, `python` и т. п. с путём выгрузки в команде;
- Read выгрузки: папка `tg-read` во временной папке (`$TMPDIR`, `/tmp`, `/var/folders`), файл из `-o`,
  `--files-dir` или `split --out-dir` этой сессии, части `*.partNN-of-NN.md` рядом с ним; Read файла с шапкой выгрузки;
- Read, Grep content и `cat`/`tail`/`grep` по папке заявок `~/.local/state/pantheon/read/` — по пути, и с offset;
- Grep в режиме content по выгрузкам. Режимы files_with_matches и count показывают имена и числа — флага нет.

Не ставят: `status`, `chats`, `folders`, `topics`, `find`, `posts --quota`, `split`, `verify` и субагент
**tg-reader**. Он и есть способ читать без флага: у него только Read, Grep и Glob, а в сессию приходит его выжимка.
Любой другой субагент, прочитавший выгрузку, ставит флаг: его пересказ идёт в сессию.

**Что спрашивается.** Хук PreToolUse отвечает ask с причиной («сессия читала сырой Telegram …; подтвердите, только
если просили это сами») на такие действия:

- WebFetch, WebSearch, SendMessage, CronCreate, ScheduleWakeup;
- Bash с сетью: `curl`, `wget`, `ssh`, `scp`, `sftp`, `nc`, `gh`, `codex` (`codex exec` — сторонний исполнитель), `git push`, `rsync` на хост, `python`/`node`/`uv`
  с `urllib`, `requests`, `httpx`, `fetch(`, `http(s)://` в аргументах или в heredoc;
- MCP: имя со словами create, update, send, post, write, delete, edit, upload, publish, comment, navigate, click и т. п.;
  любые инструменты `claude-in-chrome` и `computer-use`;
- Write, Edit, MultiEdit и NotebookEdit в память (`~/.claude/agent-memory`, `~/.claude/projects/*/memory`),
  `CLAUDE.md`, `AGENTS.md`, `~/.claude/tools|skills|agents|commands|hooks|rules`, настройки `~/.claude/settings*.json`,
  `sync.sh`, `~/ai/knowledge`, сам флаг. То же — Bash-запись туда (`>`, `>>`, `tee`, `cp`, `mv`, `sed -i`, `rm`).

Отказ guard важнее: Claude Code сводит решения всех хуков PreToolUse как deny > defer > ask > allow
([hooks](https://code.claude.com/docs/en/hooks)). taint никогда не отвечает allow.

**Режимы разрешений.** В **auto** вопрос хука показывается: «A hook's "ask" also forces a permission prompt in auto mode:
the classifier can still deny the tool call, but it can't approve the call silently» (hooks, PreToolUse decision
control; то же в [permission-modes](https://code.claude.com/docs/en/permission-modes)). В `-p` вопрос задать некому,
и действие отклоняется. В **dontAsk** всё, что требует вопроса, отклоняется. **bypassPermissions** «disables
permission prompts», а в списке того, что никакой режим не одобряет сам, вопрос хука не назван. Поэтому в этом
режиме taint отвечает deny вместо ask. Живая проба — у лида.

**Как снять.** Ваше следующее сообщение (UserPromptSubmit). Не снимают: уведомление фоновой задачи
(`<task-notification>`), сообщение другой сессии («Another Claude session sent a message:»), сообщение канала
(`<channel`). Поле события `source` (Claude Code 2.1.29x): флаг снимает только `user` или событие без поля.
Пробуждение и запуск по расписанию (`loop_wakeup`, `schedule_wakeup`, `poll_event`), системный промпт (`system`) и
SDK (`sdk`) флаг не снимают — так же журнал owner-log в pantheon решает, что текст писали не вы. Поля `origin.kind` и
`promptSource`, если Claude Code начнёт отдавать их хуку, тоже учитываются. Флаг одной сессии на другие не влияет.
Флаги старше 7 дней удаляются. Выключить правило — `GUARD_OFF=tg-taint`.

**Сбой.** PreToolUse — код 2 и `onFailure: block`: действие остановлено. PostToolUse — флаг ставится, если в событии
есть tg-read. UserPromptSubmit — код 0, чтобы не блокировать ваше сообщение. Каждый сбой — строка в
`guard-failures.log` без текста события.

**Чего не ловит.**

- Программу изнутри: `python script.py`, который сам читает выгрузку или ходит в сеть.
- Сеть мимо списка команд и Bash-запись мимо простых шаблонов (`python -c "open(...).write"`).
- Выгрузку, скопированную в другое место (`cp` и потом Read копии), если в копии нет шапки и чтение не с начала.
- Сырой текст, пришедший не через tg_read: канал Telegram в сессии, вставка владельцем, MCP Telegram.
- Действия наружу без слов из списка: Artifact, MCP с именами вроде `batch` или `run`.
- Субагента, запущенного до флага: его PreToolUse проверяется по тому же session_id, но то, что он уже сделал, не
  отменяется.

## Слияние PR: три режима и шлюз слияния (metis-0038, guard 0.5.0; шлюз слияния — P1-4, guard 0.5.4)

**Шлюз слияния, коротко.** С guard 0.5.4 `gh pr merge` проходит, только если то, что проверено, — ровно то, что сливается.
Поштучного «да» владельца на PR больше нет: `--subject "[metis-NNNN] …"`, ответ окна вопросов в zeus.md, отметки
`merge-consent/` и таблицу `[merge_protect]` guard не читает. Их заменил журнал проверок
`~/.local/state/pantheon/merge-gate/records.jsonl`. Ядро защит (Д3) по-прежнему сливает только сам владелец.

**Ядро — по Touch ID (metis-0285, guard 0.5.13).** PR ядра защит владелец сливает одним прикосновением пальца, а не
командой gh. Роль ставит заявку `pantheon merge request N -R <owner/repo>`. Плановый проход (launchd, вне песочницы
окон) заново сверяет [merge_repos] и шлюз на тот же head и показывает окно Touch ID «Слить <repo>#N (<sha7>), файлов N,
ядро: <задетые файлы ядра>. argus ×2 ✓, CI ✓. Заголовок: «…»». После пальца он под блокировкой очереди ещё раз сверяет,
что заявку не сняли и не заменили и что шлюз в силе (новый «вернуть» или коммит за время окна — не сливать), и только
тогда пишет строку `<время> merge-approve <owner/repo>#N <sha>` в `~/.local/state/pantheon/owner-log/merge-approve.log`
и сливает `gh pr merge N --match-head-commit <sha> --merge`. Шлюз guard пускает слияние ядра, только если такая строка
есть на тот же репозиторий, номер и SHA и ей не больше суток (время из будущего или без пояса — не в силе); новый коммит
требует новой заявки и нового пальца. Строку пишет только проход: owner-log закрыт ролям песочницей, а
`pantheon merge run` ролям закрыт правилом pantheon-acl (им — только `request`, `status`, `cancel`). Помощник окна —
только свой бинарник в `~/.local/state/pantheon/bin` с отметкой sha256 исходника: переменной на подмену помощника нет.
Окно не показать из launchd — запасной путь: уведомление, щелчок по нему запускает `pantheon merge run --click` от
имени владельца.

Окружение прохода задаёт launchd, а его меняет любой процесс владельца (`launchctl setenv`). Поэтому проход строит
окружение с нуля (metis-0303). HOME у него — realpath домашней папки учётной записи: HOME окружения только
сверяется с ней, а путь через ссылку дальше не идёт. PATH у него постоянный, STATE, папка Пантеона и current — от HOME.
`PANTHEON_STATE`, `PANTHEON_NOTIFY_LOG`, `PANTHEON_FAKE_*`, `GH_CONFIG_DIR`, токены gh и прочее из окружения он не
берёт. Плановый проход не берёт `PANTHEON_PYTHON`, `PANTHEON_PY_DIRS` и `PYTHONEXECUTABLE` (на macOS она задаёт
интерпретатор даже при `-I`). Кандидата он проверяет с `-I`, а config.toml с интерпретатором читает от домашней папки
учётной записи, не от HOME и не из `PANTHEON_STATE`. Проход слияния и щелчок идут интерпретатором, который нашёл
плановый проход. В остальном плановый проход ещё читает launchd-окружение, и `DYLD_*` доходит до его интерпретатора. Целиком этот путь закрывает только запрет ролям `launchctl setenv` (metis-0298).

**Включение.** Новая схема включается строкой `[merge_client]` в policy.toml (даже пустой таблицей) — это шаг
Метиды. До этого для своих папок всё как в 0.4.7: сливают только направления из `[merge]`, в его папках, `-R` — из
`[merge_repos]`; Гермес и Афина без `[merge]` не сливают. Режим защит, шлюз слияния и все проверки сбоев действуют сразу.
Внутренние папки Метиды без `[merge]` до включения закрыты. После выпуска 0.5.4 каждому сливающему направлению нужна
строка в `[merge_repos]` со всеми его репозиториями, и своими тоже: без неё шлюз слияния закрывает слияние даже без `-R`.

`gh pr merge` разрешён главной сессии координатора направления (`domain-coordinator` без `agent_id`) и лиду
этого направления (metis-0054, guard 0.5.2). Лид — субагент `hephaestus-<short>` или `apollo-<short>`, где short —
имя направления папки запуска (domains.json) после первого «-»: так роли собирает `pantheon roles build`
(hermes-site → hephaestus-site, metis-pantheon → hephaestus-pantheon). Дальше лид проверяется как координатор: те же
режимы, личное и шлюз слияния. Лиду чужого направления, сессии без направления (Пританей ~/ai/pantheon) и
остальным субагентам — dev-*, argus, talos, prometheus — отказ: они отправляют свою ветку, открывают PR и пишут в
отчёте лиду, что проверено и что меняется. Пританею и мастерской — тоже отказ. Координатор с личным в папке
(mnemo-brain, `[private]`) и его лид не сливают, как и не отправляют: третье свойство (наружу) им закрыто.
Лид узнаётся по имени роли и папке запуска сессии; кто его позвал, guard не видит. Поле `leads` реестра guard
не читает: `apollo-<short>` проходит и у направления без лида дизайна — такой роли просто нет среди собранных.

Режим guard выбирает по папке, из которой запущена команда (cwd сессии, без `cd` в самой команде), и по
репозиторию, в который сольёт gh:

| Режим | Где | Кто | Что шлюз слияния требует сверх общего |
| --- | --- | --- | --- |
| Защиты | папки `[coordinators] metis-pantheon` (agent-kit, ~/.claude…) или их репозиторий | только Метида и её лид | Д3: PR не задевает ядро защит |
| Продукт | `[merge_client]` направления | координатор этого направления и его лид | запись talos и строка «что ушло» с откатом |
| Внутреннее | папки своего направления из domains.json (и `[merge]` — для совместимости) | координатор этого направления и его лид | — |

**Что проверяет шлюз слияния во всех режимах** (код — `hooks/merge_gate.py`):

1. Один номер PR, без `--auto` и `--admin`, ровно один `--match-head-commit <SHA 40 знаков>`. GitHub сольёт PR,
   только если его голова — этот коммит, поэтому слияние не уедет на непроверенный код.
2. Все репозитории команды (`-R`, а без него — remote папки и gh-resolved) — из `[merge_repos]` своего направления,
   и репозиторий ровно один.
3. В журнале есть запись тестов `tests` на этот SHA в этом репозитории.
4. Вердикты argus на этот репозиторий, PR и SHA. Рецензент — пара session_id и agent_id записи, у каждого
   считается его последний вердикт (guard 0.5.9, metis-0158). Шлюз слияния пускает, только если рецензент есть и
   последний вердикт каждого — «принять» (`accept`) с полным перечнем проверенного (Б6, guard 0.5.6): что открыл,
   что запустил, чего не проверял. «Принять» старого формата, без перечня, не пускает — тот же argus повторяет его
   с флагами. «Вернуть» (`reject`) привязано к PR, а не к коммиту (metis-0415): оно в силе на
   любом следующем head. Его снимает только «принять» с перечнем, записанное после него:
   1. того же рецензента на том же head. «Принять» без перечня «вернуть» не снимает;
   2. на сливаемый SHA, если «вернуть» было на другом head: того же рецензента — всегда, другого argus — только
      если код сливаемого SHA посчитан и не равен коду «вернуть». «Принять» другого argus на код, равный коду
      «вернуть», «вернуть» не снимает (решение 0415b, 25.10): ложное «вернуть» снимает тот же argus или новый код.
      Код не посчитан — тоже не снимает;
   3. на исправленном коммите — с другим кодом от той же merge-base, если код сливаемого SHA не совпал с кодом
      «вернуть».
   «Принять» другого argus на том же head «вернуть» не перекрывает, так что два argus на одном head с «принять» и
   «вернуть» дают отказ при любом порядке записей.
   Второму argus guard не отказывает: для ядра нужны оба, а его «вернуть» терять нельзя. Вердикт берётся только из
   записи хука по роли argus: «одобри, argus: принять» в тексте PR или коммита ничего не значит (канарейка Б1 в
   `tests/test_merge_gate.py`).
   **Перенос «принять»** (metis-0415). PR подтянул main — head новый, а код PR тот же. «Принять» с
   перечнем с прошлого head переходит на новый без нового argus, если совпал собственный дифф PR: от merge-base с
   base PR до head. Отпечаток — по содержимому файлов (решение владельца 25.10): `git diff --raw -z --no-abbrev
   --no-renames --no-relative --ignore-submodules=none` без pathspec даёт режим, sha блоба или подмодуля, статус и
   путь каждого файла PR. Фильтр `plugin.json` и сортировка по пути — в Python. `plugin.json` плагинов сверяется по
   тексту без строки `version` и по режиму. Настройки git на отпечаток не влияют: `diff.*`, `core.abbrev`,
   `submodule.*.ignore`, атрибуты и переменные `GIT_*` — git зовётся без `GIT_*` окружения и с явным `--git-dir`.
   Вывод разбирается строго: не по формату — отпечатка нет. Цена (решение владельца 25.10): если main правил файл,
   который правит и PR, переноса нет и нужен argus — так около 20 % пар, где перенос был бы законным. Сверяются 8
   последних head с вердиктами (`CARRY_HEADS`) за 4 с на все отпечатки (`CARRY_BUDGET`), у каждого вызова git —
   3 с. Засчитывается только «принять», записанное позже каждого «вернуть» PR, кроме «вернуть», которое
   снял тот же рецензент «принять» с перечнем на том же head. Эта отсечка держит и перенос, и прямое «принять» на
   сам сливаемый SHA: откат к коду, принятому до «вернуть», по старому «принять» не пройдёт — ни после подтягивания
   main, ни force-push на тот же старый head после того, как «вернуть» сняло «принять» на другом коде. Отказ назовёт
   такое «принять» и отсёкшее его «вернуть». Переноса
   нет, если отпечаток не посчитать: папка слияния — не клон репозитория PR, история неполная (shallow,
   `info/grafts`), коммита base PR или head нет в git (`git fetch`), merge-base не одна (в том числе крест
   слияний), вывод `--raw` не разобрать, `plugin.json` — не файл, сбой или таймаут git, старый git без нужного
   флага. Подмены `git replace` при сверке не действуют. Записи тестов и `talos` не переносятся: на новом head
   нужны свои. Каждый перенос — строка в `merge-gate/carry.jsonl` (`kind: carry`, PR, SHA, base, отпечаток, с
   каких «принять», кто сливает); `records.jsonl` он не меняет. Строка не записалась — отказ.
   **Гонка проверки и слияния (TOCTOU) шлюз не закрывает.** Хук смотрит журнал в момент вызова `gh pr merge`.
   Если argus запишет «вернуть» после того, как хук пустил команду, слияние уже идёт и не остановится: вердикт,
   записанный позже проверки, на него не влияет. `--match-head-commit` держит только коммит, а не журнал. Поэтому
   сливают, когда все вызванные argus уже ответили; PR ядра сливает владелец. Смысловой конфликт с main при том же
   собственном диффе PR — тоже вне шлюза: перенос судит по коду PR (решение владельца 24.10).
   В режиме защит (guard 0.5.10, metis-0176) в PR, который задевает ядро, «принять» засчитывается, только если `ran`
   начинается с «модель: claude-opus»: «принять» с другой моделью шлюз не считает, и проверку повторяет argus на Opus.
   Вне ядра (упрощение п. 9, 27.10) хватает одного «принять» argus на любой модели, в том числе на Sonnet: ядро ли
   PR, шлюз решает тем же `_core_problem`, что и Д3 (список файлов PR из gh); не удалось проверить — считается ядром.
   Незаменённый шаблон `<ID>` в `--ran` — отказ с подсказкой подставить ID модели, и в `pantheon review`, и в шлюзе.
   Модель шлюз берёт ещё и из данных сессии argus, а не только с его слов: хук при записи `accept` и `reject` читает
   транскрипт argus и кладёт в запись поле `models` — значения `message.model` его ответов. В PR ядра «принять»
   засчитывается, только если все эти модели — Opus и среди них та, что названа в `--ran` (тот же ID или он с
   датой). Сменилась модель в ходе проверки (запасная после отметки защиты Anthropic) — «принять» не засчитан.
   Путь к транскрипту Claude Code в PreToolUse и PostToolUse не передаёт (`agent_transcript_path` есть только в
   SubagentStop). Хук выводит его из входа: `<папка transcript_path>/<session_id>/subagents/agent-<agent_id>.jsonl`,
   у argus, запущенного через Workflow, — `subagents/workflows/<runId>/agent-<agent_id>.jsonl` (metis-0413), у главной
   сессии argus — сам `transcript_path`. Своего файла у субагента нет — главный транскрипт вместо него не читается: это
   сессия того, кто позвал argus. Симлинк не читается. Транскрипта нет — как раньше, по `--ran`, а в записи пометка
   `models_note`. Транскрипт найден, а моделей в нём нет (например, Claude Code сменил формат) — в записи
   `models: []` и своя пометка, а в защитах такое «принять» не засчитывается: отказ называет причину, сверка не
   выключается молча.
   В других режимах модель не проверяется.
5. Рецензенты — не сливающий: пара session_id и agent_id ни у одного из них не совпадает с той, что сливает.
6. Продукт: ещё запись `talos` на этот PR и SHA и строка в `~/ai/pantheon/alerts.md` вида
   `YYYY-MM-DD HH:MM · кто · …` со ссылкой `owner/repo#N` и словом «откат» (её пишет `pantheon alert`).
7. Защиты: Д3 — `gh pr view N -R <repo> --json headRefOid,changedFiles` и список файлов

   регистра; решение владельца 15.10, metis-0092) и `.claude-plugin/marketplace.json` — откуда ставятся плагины,
   его подмена увела бы источник guard (metis-0115, guard 0.5.6). С guard 0.5.10 в ядре ещё общие роли
   `plugins/pantheon/roles/**` и правила окон `plugins/pantheon/lib/window_rules.py` (metis-0174, 0182). С metis-0598
   (решение владельца 30.10) — ещё журнал ваших слов и регистрация хуков Пантеона `plugins/pantheon/hooks/ctx.py` и
   `plugins/pantheon/hooks/hooks.json`, слияние по Touch ID `plugins/pantheon/lib/merge.py`, карта плагинов и MCP
   `plugins/pantheon/lib/plugin_map.py` и `plugins/pantheon/plugins-by-role.toml`; соседние файлы тех же папок — не
   ядро. Проверяются и новый путь, и `previous_filename`, так что вынос
   файла из guard тоже виден. С metis-0404 в ядре и сборка окон в `plugins/pantheon/lib/pantheon.py`, но не весь файл:
   шлюз берёт старый и новый pantheon.py из папки слияния (base и head PR, одна merge-base) и сравнивает по AST
   функции `sandbox_build`, `domains_build`, `run_settings` и всё, что они транзитивно зовут и читают в этом файле,
   с каждым верхнеуровневым присваиванием и изменением этих имён (`X.append`, `X[k] =`, `global X`). Имена — объединение
   замыканий на merge-base, head, base PR и живой вершине ветки base (`gh api …/git/ref/heads/<base>`): соседний PR,

**Как появляются записи.** Журнал пишет только хук guard на PostToolUse, после успешной простой команды
`pantheon review <вид> …` — без `;`, `|`, `&`, `$(`, обратных кавычек, перенаправлений и переводов строки. Сама команда
`pantheon review` (плагин pantheon) ничего не пишет: она проверяет формат и запускает тесты.

- `pantheon review test -- <команда тестов>` — в чистом дереве git, запись `tests` на HEAD и репозитории remote.
  Код выхода — код команды; упала команда — хук не пишет (PostToolUseFailure записей не делает). Команда меняет
  HEAD или пачкает дерево — код 3, записи тоже нет. Программа после обёрток (`heavy`, `env VAR=…`, `time`, `nice`,
  `timeout N`) — `true`, `:`, `echo`, `printf`, `exit`, `test`, `[`, `sleep` или `yes` — отказ на PreToolUse и
  записи нет: такая команда ничего не проверяет. С 0.5.8 (metis-0157) пустыми считаются и python без скрипта или
  с `-c` из `pass`, литералов и `print`/`exit` с литералами (`python3 -c pass`, `python3 -c ''`), и оболочка без
  скрипта или с `-c`, где команда пустая (`sh -c ''`, `bash -c 'true'`). С 0.5.9 (metis-0164) python — это и
  `python3.14t`, и `pypy3`. С 0.5.10 (metis-0177) обёртками считаются и присваивания перед командой (`VAR=x true`),
  и `uv run`, а пустыми — `uv run python` без скрипта и `node` без скрипта (`node`, `node -v`, `node -e 0` — `-e`/`-p` с литералами,
  `process.exit` и `console.log` литерала). Слово, которое разбор не вычислил (`python3 -I $UNSET/tests/run.py`), пустым не
  считается. Относительный путь (`./test`, `bin/test`) — скрипт проекта, а не программа из списка; `/usr/bin/true`
  судится по имени. С metis-0194 обёртки — ещё `command`, `exec` (`-a имя`), `npx`, `uvx` и `uv --directory x run`;
  пустые — `command -v`/`-V` (печатает путь, а не запускает), `node -pe 1` и слова после кода `-e`/`-p`
  (`node -pe 1 pytest`: это `process.argv`, а не скрипт), `node --check` без скрипта.
- Вторая запись `tests` — от планового прохода Пантеона (`pantheon outside test` и тесты после «принять» argus,
  `plugins/pantheon/lib/outside.py`, [sb-simplify] п. 7), `by.agent_type` = `pantheon-outside`. Её пишет только
  проход вне окон: роли STATE закрыт, а команде под его профилем `sandbox-exec` — тоже. Запись есть только у проверки
  проекта (`.pantheon-verify`, иначе test/check package.json, иначе pytest), с `--script` и у dev-сервера её нет; команда
  видна в поле `cmd` — у скрипта package.json с телом, у строки `.pantheon-verify` из файла ветки — с пометкой.
- Обёртка review test судится как голая команда (0.5.8, metis-0157): команду после `--` guard проверяет теми же
  правилами, что без обёртки. `pantheon review test -- gh pr merge … --admin`, `… -- git push origin HEAD:main`,
  запись в защищённое — тот же отказ, что у голой команды; так же для `pantheon.py` через python и оболочку.
  `heavy` разбор Bash тоже видит как обёртку: `heavy git push origin main` закрыт, как `git push origin main`.
- `pantheon review accept <owner/repo> <PR> <SHA> --opened "<что открыл>" --ran "<что запустил>" --unchecked "<что
  не проверял>"` — записывается, только если роль — argus и все три поля есть и непусты (`--ran=…` тоже можно);
  в записи — `"checklist": {"opened", "ran", "unchecked"}`. `reject` — те же флаги по желанию. Значения — без `;`,
  `|`, `&`, `<`, `>`, `$(`, обратных кавычек и переводов строки (правило простой команды); кавычки и пробелы внутри
  поля можно.
- `pantheon review talos <owner/repo> <PR> <SHA>` — только если роль — talos.
- `pantheon review status [<owner/repo> <PR>]` — показать записи.
- `pantheon review report <owner/repo> <PR> <agent8>[/<сессия8>] [--out ПУТЬ]` (metis-0602) — последний отчёт прежнего
  argus по PR из его транскрипта `~/.claude/projects/*/<сессия>/subagents/agent-<id>.jsonl` (пара — из `review status`).
  Нужна, когда SendMessage к argus после /clear отвечает «No transcript found»: новый argus сам вызывает её на каждую
  пару из «вернули» и ведёт повторный круг по дельте. Пара и последний head — из журнала шлюза (вердикт argus на этот
  PR); «Head:» отчёта обязан равняться ему. Нет вердикта, транскрипта (симлинк не читается), отчёта, несколько
  совпадений или «Head:» не тот — отказ, код 1; `--out` только под $TMPDIR или /private/tmp (иначе 2), файл не
  перезаписывается. В журнал не пишет.

Фоновая команда записи не даёт: для неё PostToolUse приходит при запуске, а не по итогу, а PostToolUseFailure не
приходит вовсе. Поэтому хук не пишет, если во входе `run_in_background`, в ответе `backgroundTaskId` или ответ — не
словарь.

Не той роли или с плохими аргументами `pantheon review accept|reject|talos` получает отказ сразу на PreToolUse:
иначе команда прошла бы, а записи не появилось. Так же сразу отказ для `pantheon review test|accept|reject|talos` в
фоне и не простой командой. argus ещё запрещены `git commit`, `merge`, `rebase`, `cherry-pick`,
`am`, `revert`, `pull`, `commit-tree`: рецензент не меняет то, что проверяет.

**Почему журнал не подделать ошибкой агента.** Папку `~/.local/state/pantheon/` роли не пишут (pantheon-acl), а
вид записи и роль автора хук берёт из события Claude Code (`agent_type`), а не из текста команды. Файл журнала —
0600 в папке 0700, только дозапись, без перехода по симлинку. Папка журнала или файл — симлинк, файл не читается —
слияние закрыто. Битые строки при чтении пропускаются. В режимах `--strict` и `--managed` записи не делаются:
журнал пишет только хук плагина. Выключатель — `GUARD_OFF=push`.

**Защиты узнаются по пути и по репозиторию.** gh сливает в репозиторий из git remote папки, а не в папку. Поэтому
guard читает `git remote -v` у каждой папки защит с `.git` и сверяет с репозиторием команды: значением `-R`, а без
него — remote папки cwd и `remote.<имя>.gh-resolved` (gh repo set-default, кроме «base»). Клон, форк с
set-default, worktree или симлинк agent-kit в любой папке — тоже защиты. Сверка идёт по owner/repo без хоста:
псевдоним ssh (`git@gh-alt:latark/agent-kit`) gh понимает как github.com. Проверка идёт
раньше реестра: если domains.json по ошибке отдаст agent-kit другому направлению, слить его сможет только Метида.
Реестр для слияния — только `~/.local/state/pantheon/domains.json`, без отката на старый
`~/.claude/hooks/domains.json`: там направления шире.

**Своя папка — по самому длинному корню.** Владелец cwd — направление с самым длинным совпавшим корнем в
domains.json, и оно должно совпасть с направлением папки запуска. Корень вроде «~/projects» у одного направления
не открывает папку другого внутри.

**Любой сбой — отказ.** Нет policy.toml, нет непустого списка `[coordinators]
metis-pantheon`, `[private]` или domains.json не разобрать, git не ответил, у папки защит с `.git` не читается
remote, cwd не репозиторий или без remote, журнал проверок не читается, gh не ответил — слияние закрыто.

**Пределы.**

- guard — хук PreToolUse: он проверяет состояние в момент вызова. Что изменится после его «можно» и до запуска gh
  (подмена симлинка cwd, правка git config), он не видит. Это уже намеренный обход, граница — песочница окна.
- guard не проверяет, правдива ли строка «что ушло» в alerts.md и перечень в «принять» argus, и что команда
  тестов — настоящие тесты. Он ловит только ошибку по короткому явному списку: пустую программу после обёрток
  (`true`, `echo ok`, `heavy :`, `env X=1 timeout 60 sleep 1`, с 0.5.8 — `python3 -c pass`, `sh -c ''`, `bash -c
  'true'`). Придуманную пустышку (`python3 -c "import os"`, `gh pr view 1`) он не ловит — это уже обход, разбор
  ради него не наращиваем. Настоящесть тестов — обязанность роли и предмет проверки argus: он пишет
  в `--ran`, что запустил сам.
- Запись `tests` от `pantheon outside test` — тот же остаток, что у `pantheon review test`: команду берут файлы, которые
  PR меняет сам (скрипт test/check в package.json; `.pantheon-verify` ветки, когда в клоне нет origin/HEAD, origin/main
  или origin/master с этим файлом; и сами эти ссылки роль может переставить в своём клоне). Пустую программу проход
  отсекает тем же коротким списком, а настоящесть команды из поля `cmd` сверяет argus.
- Профиль `pantheon outside` (`sandbox-exec`) — «разрешено всё, кроме списка»: ключи (`.env*`, `secrets/`, `~/.ssh`,
  `~/.npmrc`, пароль демона CDP, Связка ключей), запись в состояние, ядро, `~/.claude`, `~/.nvm` и кэши окон, порты
  браузеров и местного прокси закрыты. Чтение папок других направлений и прочая сеть открыты — это остаток: тесты и
  dev-сервер проекта иначе не работают, а ключей и браузера со входами им не достать.
- Не ловятся и так задуманы (защита от ошибки, не от обхода, metis-0164): пустышки вроде `python3 -c 'import
  sys'`, `node -e 0`, `gh pr view`; `$X review test -- …` и `python3 "$UNSET/pantheon.py" review test -- …` — имя
  пульта не вычислить, и команда после `--` не судится как голая; при невычисленном имени команды `check_push`
  ищет среди слов только `push`, а не `merge`.
- Список файлов сверяется с `changedFiles`; если gh отдал неполный список (предел API — 3000 файлов), PR защит закрыт.
- Ядро — весь `plugins/guard/**`, casefold; файлы из `pulls/N/files` с `previous_filename`. Д3 опирается на то,
  что `guard_rules.py` зовёт `merge_gate.py`; правку `guard.py` или `guard_rules.py`, которая это ломает, Д3 тоже останавливает: весь `plugins/guard` — ядро.
- «Один номер PR» — на один вызов `gh pr merge`: `gh pr merge 5 … && gh pr merge 6 …` пройдёт двумя слияниями,
  каждое — со своими записями. Счётчика на всю команду нет, разбор Bash не наращиваем.

Везде закрыто: `--admin` (и `--admin=…`), `--auto`, `GH_REPO`/`GH_HOST`, `cd` в команде, PR ссылкой или `$N` вместо
номера, `-R` не из `[merge_repos]` своего направления, `gh api` с записью, push в main и master.

    sudo install -m 644 ~/.claude/plugins/marketplaces/agent-kit/plugins/guard/managed-settings.json \
      "/Library/Application Support/ClaudeCode/managed-settings.json"

Файл — `managed-settings.json` рядом с этим README: запреты (ключи в Связке, `.env`, разрушительный git,
`rm -rf`, terminal-notifier) и хук guard из клона маркетплейса. Обновить — та же команда после обновления
маркетплейса. Проверка: в папке с `.claude/settings.json`, где разрешено `Bash(git clean *)`, команда
`git clean -n` всё равно получает отказ.

С metis-0571 хук в этом файле — `/bin/sh …/hooks/python.sh …/hooks/guard.py --managed`: запускатель
ищет Python 3.11+ (`python3.14`…`python3.11` в `/opt/homebrew/bin`, `/usr/local/bin`, python.org и PATH, затем
`python3` из PATH с проверкой версии) и без него останавливает PreToolUse кодом 2. Уже поставленный файл со старой
командой `python3 …/guard.py --managed` продолжает работать: guard.py на Python ниже 3.11 сам перезапускается через
`hooks/python.sh`. Переустановить файл той же командой `sudo install` — по желанию, чтобы хук не тратил лишний запуск
системного Python. С metis-0148 старый Python разбирает только короткий вход `guard.py`, а не все правила.

## Данные и выключатель

- `~/.local/state/pantheon/domains.json` — карта направлений, собирает `pantheon domains build` из
  `~/ai/pantheon/directions.toml`;
- `~/.claude/pantheon/policy.toml` — привилегии (кто metis-pantheon и mnemo-brain, доступ к личному, `[merge_repos]`),
  что закрыто Пританею (`[hq]`: папки `closed_dirs`, коллекции qmd `closed_collections`) и имена корпуса
  (`[corpus]`); без раздела — пусто, в коде своих значений нет;
  образец — `policy.example.toml`, правит только metis-pantheon;
- `~/.local/state/pantheon/merge-gate/records.jsonl` — журнал проверок шлюза слияния, пишет только хук guard
  (PostToolUse), смотреть — `pantheon review status`;
- `~/.local/state/pantheon/merge-gate/carry.jsonl` — журнал переносов «принять» шлюзом слияния (metis-0415), пишет
  только хук guard (PreToolUse) перед тем, как пустить слияние;
- `~/.local/state/pantheon/guard-strict/<session_id>` — метка строгого guard окна (окно и инструменты, без текста
  команд): по ней хук плагина той же сессии молчит (metis-0148);
- `~/.local/state/tg-taint/<session_id>` — флаг tg-taint (время и источник, без текста), `<session_id>.dumps` — пути
  выгрузок из `-o`, `--files-dir`, `--out-dir` этой сессии;
- выключить правило: `GUARD_OFF=dev-server,nextjs` в `env` файла settings.json (`push` выключает и запись журнала шлюза слияния).
